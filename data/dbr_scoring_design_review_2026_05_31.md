# DBR Scoring Design Review — 2026-05-31

## The Current Formula

```
final_score = topic_fit × 80% + style_fit × 20%
```

### The 80% — Topic Fit

- User selects k topics (D01–D12)
- For each topic, user sets a direction:
  - identity_anchor: עמדות 38%, תדמית 42%, ביצוע 20%
  - capability_operator: עמדות 28%, תדמית 12%, ביצוע 60%
  - identity_and_capability: עמדות 33%, תדמית 25%, ביצוע 42%
  - squad_representation: same as identity_anchor
- Each score is adjusted by confidence: `adjScore = v × (0.6 + 0.4 × conf/100)`
- topic_fit = average of all selected topic scores

**Issue:** If user selects only 1 topic → that topic = 80% of final score. Too sensitive to one data point.

---

### The 20% — Style Fit (4 questions)

| Question | SM fields used | Weight |
|---|---|---|
| Public tone | סגנון + סגנון_ביטחון → matrix | 5% |
| Knesset role | תפקיד_מאבק / חקיקה / חיבור | 6% |
| Info tolerance | נושאים_מכוסים | 4% |
| Proven/potential | נושאים_מכוסים + ממוצע_עמדות | 5% |

#### Question 1 — Public Tone (5%)
- Compatibility matrix 4×4 (combative / statesmanlike / bridging / mixed)
- Max match = 94 (not 100 — by design)
- Multiplied by confidence modifier (CONF_M: גבוה=1.0, בינוני=0.88, נמוך=0.65)
- `score = mat[user_choice][candidate_style] × confidence × 5%`
- If user chose "mixed_tone" → everyone gets flat 72, no differentiation

#### Question 2 — Knesset Role (6%)
- Candidate has 3 independent scores (1–10): campaigner, legislation, bridging
- User picks one role → system takes that score × 10
- No confidence modifier here
- `score = תפקיד_רלוונטי × 10 × 6%`

#### Question 3 — Info Tolerance (4%)
- Based on נושאים_מכוסים = X/12 (global, not topic-specific)
- `score = b + frac × m` where b, m depend on user's tolerance level
- **Systemic bias:** veterans (high coverage) always score higher than newcomers
- "Potential-dependent" option doesn't actually use any potential metric — just changes b/m
- If candidate covers 12/12 → always scores 100 regardless of user's answer

#### Question 4 — Proven/Potential (5%)
- `proven = frac × avg_score × 12` (breadth × depth)
- `pot = avg_score × 10` (depth only)
- User's answer weights the blend: proven_safe=85/15, balanced=55/45, interesting_potential=25/75
- Uses GLOBAL ממוצע_עמדות — not specific to selected topics

## Issues Identified

### 1. The 20% is topic-blind
All 4 style questions use global SM data, not the specific topics the user selected.
- A candidate's knesset role score doesn't change based on which topics the user picked
- proven/potential uses global average, not average for selected topics

### 2. Info tolerance and proven/potential share input
Both use נושאים_מכוסים → not truly independent dimensions.
A candidate who covers many topics wins both, regardless of user's answers.

### 3. "Potential-dependent" option is misleading
The name implies it checks for potential — but the formula doesn't. It just changes b/m parameters.

### 4. Topic count imbalance
Selecting 1 topic → 80% weight on single data point.
Proposed solution: scale topic weight by n_selected/12, normalize with style at 20%.

| Topics | topic% | style% |
|---|---|---|
| 1 | 25% | 75% |
| 3 | 50% | 50% |
| 6 | 67% | 33% |
| 12 | 80% | 20% |

But counter-argument: user who selects 1 topic WANTS that to dominate. May need minimum of 4 topics instead.

## Proposed Architecture Change (to discuss)

**Current:** 20% style questions use global SM fields (capability proxies)

**Proposed:** Replace capability-related style questions with ביצוע_ציון from NTM, specific to selected topics

```
80% → how well candidate fits user's selected topics (by direction)
20% → how much candidate has actually performed in those same topics
```

**Why this is NOT double-counting:**
- 80%: uses ביצוע weighted by per-topic direction (only counts for topics where user chose capability_operator)
- 20%: uses average ביצוע across ALL selected topics regardless of direction

**Open questions:**
1. Replace ALL 20% with NTM-based ביצוע, or only some questions?
2. What happens to public_tone question — it measures style match, not capability. Keep as-is?
3. What happens to knesset_role — does it still make sense if we use topic ביצוע directly?

## Notes on Data Quality

- All SM scores (סגנון, תפקיד_מאבק, etc.) were generated by LLM (late 2025)
- Consistent and systematic, but knowledge cutoff applies
- Less-known candidates have lower confidence / coverage scores → inherent bias
- Matrix values (94, 52, 47...) are manually chosen, not derived from research
  - This is acceptable because they apply equally to all candidates
